## 技术背景

### 项目架构

agent0-sdk-subgraph 使用**模板化多链设计**，核心特点：

1. **单一代码库**: `src/` 目录中的代码被所有链共享（95%+ 复用率）
2. **配置驱动**: 每条链通过 JSON 配置文件定义合约地址和网络参数
3. **模板生成**: 使用 `config/subgraph.template.yaml` + 网络配置 → 生成各链的 `subgraph.yaml`
4. **独立构建**: 每条链可单独构建和部署

### 核心组件

#### 1. Schema 定义 (`schema.graphql`)

7 个核心实体类型：

```graphql
type Agent @entity {

  feedback: [Feedback!]! @derivedFrom(field: "agent")
  validations: [Validation!]! @derivedFrom(field: "agent")
  metadata: [AgentMetadata!]! @derivedFrom(field: "agent")

  lastActivity: BigInt!

  id: ID!                           # "chainId:agentId:clientAddress:feedbackIndex"

  id: ID!                           # "feedbackId:responseIndex"
  feedback: Feedback!
  responder: Bytes!
  responseUri: String
  responseHash: Bytes

  totalValidations: BigInt!         # 总验证数
  completedValidations: BigInt!     # 完成验证数

  lastActivity: BigInt!
  updatedAt: BigInt!

  active: Boolean

  mcpVersion: String
```

#### 2. Event Handlers (AssemblyScript)

三个注册表的事件处理器：

**Identity Registry** (`src/identity-registry.ts`):
- `handleAgentRegistered(event: Registered)` - Agent 注册
- `handleMetadataSet(event: MetadataSet)` - 元数据设置
- `handleUriUpdated(event: UriUpdated)` - URI 更新

**Reputation Registry** (`src/reputation-registry.ts`):
- `handleNewFeedback(event: NewFeedback)` - 新反馈
- `handleFeedbackRevoked(event: FeedbackRevoked)` - 反馈撤销
- `handleResponseAppended(event: ResponseAppended)` - 响应追加

**Validation Registry** (`src/validation-registry.ts`):
- `handleValidationRequest(event: ValidationRequest)` - 验证请求
- `handleValidationResponse(event: ValidationResponse)` - 验证响应

#### 3. IPFS 集成

使用 File Data Sources 索引 IPFS 上的 Registration Files：

```yaml
templates:
  - name: AgentRegistrationFile
    kind: file/ipfs
    mapping:
      apiVersion: 0.0.7
      language: wasm/assemblyscript
      file: ./src/registration-file.ts
      handler: parseRegistrationFile
      entities:
        - AgentRegistrationFile
      abis:
        - name: IdentityRegistry
          file: ./abis/IdentityRegistry.json
```

#### 4. Greenfield 适配说明（当前策略）

- 现有 Subgraph 的文件数据源是 `kind: file/ipfs`，`src/utils/ipfs.ts` 只在 URI 判定为 IPFS 时才触发文件下载和解析；gnfd:// 或普通 HTTP/HTTPS URI 不会被 Graph Node 下载，`registrationFile`/`feedbackFile` 将为空。
- The Graph Studio/Hosted/Network 暂无 `file/greenfield`，要直接索引 Greenfield 需自研 Graph Node 下载器扩展或中间层将 Greenfield 文件镜像到 IPFS，并在链上写入 IPFS CID。
- 工作量较大，当前不在本次范围内，保持链上 URI 指向 IPFS（可在 JSON 内附带 Greenfield 链接或由 SDK 双写 IPFS+Greenfield）；后续若需原生 Greenfield 支持再单独立项。

#### Step 1.1: 创建 BSC Testnet 配置

**文件路径**: `config/networks/bsc-testnet.json`

**内容**:

```json
{
  "network": "bsc-testnet",
  "chainId": "97",
  "displayName": "BSC Testnet",
  "identityRegistry": {
    "address": "0xf04A7eEeB7f99631DD08D9C6418ED8f9a8A03292",
    "startBlock": 0
  },
  "reputationRegistry": {
    "address": "0x50100029Ac4E6F42505F5773841c03bcfB60181F",
    "startBlock": 0
  },
  "validationRegistry": {
    "address": "0x8366684cCE2266aD632bfE78E784007848E05E3a",
    "startBlock": 0
  },
  "graphNode": {
    "network": "bsc-testnet"
  }
}
```

**说明**:
- `network`: Graph Node 识别的网络名称（必须与 The Graph 支持的名称一致）
- `chainId`: 链 ID（字符串格式）
- `displayName`: 用户友好的显示名称
- `startBlock`: 建议设为 0，或者实际部署区块号以加快同步速度
- `graphNode.network`: 必须与 `network` 字段一致

## 附录

### A. 常见问题

#### Q1: 为什么 Graph Node 同步很慢?

**A**: 可能原因：
1. `startBlock` 设为 0，需要同步所有历史区块
2. RPC 端点速率限制
3. IPFS 下载 Registration Files 慢

**解决方案**:
- 将 `startBlock` 设为实际部署区块
- 使用付费 RPC 端点（如 QuickNode、Alchemy）
- 检查 IPFS gateway 配置

#### Q2: 部署后查询返回空结果?

**A**: 检查：
1. Subgraph 是否完全同步（查看 Studio Dashboard）
2. 合约地址是否正确
3. `startBlock` 是否在事件发生之前

#### Q3: IPFS Registration Files 未索引?

**A**: 可能原因：
1. IPFS gateway 不可达
2. tokenURI 格式不正确（应为 `ipfs://QmXXX...`）
3. File Data Source 未正确配置

**调试**:
- 查看 Graph Node 日志: `docker-compose logs -f graph-node | grep IPFS`
- 测试 IPFS 可访问性: `curl https://ipfs.io/ipfs/<CID>`

#### Q4: 如何更新已部署的 Subgraph?

**A**: 重新部署新版本：

```bash
# 修改代码后
npm run codegen
DEPLOYMENT=erc-8004-bsc-testnet npm run build:single

# 部署新版本（版本号递增）
graph deploy --studio bsc-testnet-agent0
# 输入新版本号: v1.0.1
```

**注意**: The Graph Studio 免费层限制为 10 次部署/天

#### Q5: 如何处理合约升级（UUPS）?

**A**: 如果合约使用 UUPS 代理模式：

1. 代理地址不变，只需更新 ABI
2. 如果事件签名变化，需要：
   - 更新 ABIs
   - 更新 mapping 代码
   - 重新部署 Subgraph

### C. 术语表

| 术语 | 说明 |
|------|------|
| **Subgraph** | The Graph 的索引单元，定义了要索引的数据和查询方式 |
| **Graph Node** | The Graph 的索引引擎，处理区块链数据并提供 GraphQL API |
| **Manifest** | `subgraph.yaml` 文件，定义数据源、事件处理器等 |
| **Schema** | `schema.graphql` 文件，定义数据模型 |
| **Mapping** | AssemblyScript 代码，处理链上事件并转换为实体 |
| **Entity** | GraphQL schema 中定义的数据类型（如 Agent、Feedback） |
| **Data Source** | 要索引的智能合约 |
| **Event Handler** | 处理特定事件的 mapping 函数 |
| **IPFS** | 去中心化文件存储，用于存储 Registration Files |
| **File Data Source** | 索引 IPFS/HTTP 文件的特殊数据源 |
| **Template** | 动态创建的数据源（如 IPFS 文件） |
| **WASM** | WebAssembly，mapping 代码编译后的格式 |
| **Gateway** | The Graph 的去中心化查询网关 |
| **Studio** | The Graph 的托管 Subgraph 平台 |
| **Deployment** | 一个 Subgraph 的特定版本和网络配置 |
